# MundusMaker 1.9.0 — what the players know, maps you can run, no terminal required

## Intended result

A DM can use MundusMaker between and during sessions without ever seeing a
terminal window. The app records what the party has learned and hands players
an offline copy of exactly that. It turns generated maps, fantasy or modern,
into prepared places, keyed rooms and planned journeys. It prints character
sheets players recognize at a glance. A new version picks up the worlds from
the old one without an export and import. Everything stays local. The existing
secrecy flags remain the only mechanism that hides anything.

Four release demonstrations define success:

1. After a session, reveal the clues and people the party discovered, run the
   safety check and export the player wiki. A player opens it from a USB stick
   with networking disabled. They can read, search and browse exactly the
   revealed material. No hidden name appears in text, links, search results,
   file names or images.
2. Populate a coastal town, key the rooms of the crypt beneath it and plan the
   journey there from the regional capital along roads and a ferry. Advance
   the campaign clock by the travel days and print a GM booklet whose keys
   match the numbers on the maps. Then do the same with a modern town: a
   downtown, suburbs, an industrial park and a rail line, keyed and populated.
3. Print D&D 2024, Vampire V5 and Call of Cthulhu 7e player sheets. A player
   who knows each game's standard sheet finds every value where they expect it
   without being told.
4. A tester running 1.8.2 from `Downloads\MundusMaker-1.8.2` extracts 1.9.0
   beside it and double-clicks the launcher. No terminal window stays open.
   The browser opens with their worlds already copied in, and a notice says
   where they came from and that the old folder is untouched. Closing the
   browser does not stop MundusMaker; Quit does, after saving.

## Preconditions (1.8.3)

1.9 builds on player-safe map output and a frozen 1.8 generator, so 1.8.3
ships first with:

- Generator guidance (IN and GOAL) removed from player renders, and room
  numbers offered as an export-time choice rather than a stored flag.
- Hash baselines for the 1.8 generation path beside the 17 legacy fixtures,
  and an automated render check that runs both sets with no new dependencies.
- A startup port check: before deferring to whatever holds the port, confirm
  it is MundusMaker and report its version and data folder.
- Folder-sync conflict copies recognized and explained, instead of being
  reported as unreadable entries.

Several items from the 1.8.3 review are feature-sized and move here: the
dungeon room key and click-to-create for generated places (Map keys,
Populate), saved handout packets, the player wiki export, and the
compare-and-adopt screen for sync conflicts.

## Install and upgrade without a terminal

This section can ship ahead of the rest. Testers need it now, and it depends
only on the preconditions.

| Feature | Change | Acceptance evidence |
| --- | --- | --- |
| Background running | Every launcher starts the server without a lasting console window. A tray icon (Windows) or menu-bar item (Mac) offers Open, data folder, startup log and Quit. Settings has **Quit MundusMaker** on every platform | No console stays open on Windows; closing the browser leaves the app running; Quit stops it only after pending saves finish |
| Single instance | Launching again opens the running app. If an older MundusMaker or another program holds the port, the launcher says so in plain words instead of silently opening it | A second launch never starts a second server; an old version on the port is named in the message |
| Automatic upgrade | On first start, find older installs in the same parent folder and bring their worlds in. Copy automatically in the unambiguous case; otherwise ask once | Demonstration 4 works; the old folder's bytes are unchanged; running it twice creates no duplicates |

### Background running contract

- **Windows:** `Start-MundusMaker.bat`, which testers already double-click,
  now starts the tray host hidden, and so do the Start-menu and Desktop
  shortcuts. A brief flash while it starts is acceptable; a window that stays
  open is not. The old visible-window behavior moves to
  `MundusMaker-Console.bat`, the always-works fallback and troubleshooting
  path, which `Start-MundusMaker.bat` also falls back to when PowerShell
  can't run. The tray script stays ASCII-only (AGENTS.md).
- **Mac:** `MundusMaker.app` already runs without Terminal and has a menu-bar
  item with Open, logs and Quit. Keep it as the documented way to start; the
  `.command` file becomes the fallback.
- **Linux:** a launcher that starts the server in the background and opens the
  browser, plus an optional `.desktop` entry. Linux has no zero-dependency
  tray, so in-app Quit is the stop control there.
- **Quit is graceful everywhere.** The tray's Exit no longer force-kills the
  process. Quit asks the server to stop accepting writes, lets in-flight saves
  finish, then exits. The in-app button flushes the current tab's pending
  saves first. Other open tabs keep their drafts and show the normal save
  warning. Quit is disabled in container mode, where Docker owns the lifecycle.
- **Nothing important goes only to a console.** The server writes a rotating
  log under the config folder (not the data folder, so sync tools don't carry
  it). Startup failures surface through the launcher: a message box on
  Windows, an alert on Mac, a local help page on Linux.
- The server still binds 127.0.0.1 only and still advertises `localhost`.

### Automatic upgrade contract

Builds on the 0.11 migration (`detectInstallData`, `/api/scan-installs`,
`/api/migrate-install`). Everything stays copy-only: nothing at the source is
ever written, moved or deleted.

- **When:** first start of an install whose data folder holds no user worlds
  (only the freshly seeded sample, or nothing). Later, the existing Import
  card remains the manual path.
- **Automatic only when unambiguous:** exactly one older install in the same
  parent folder has worlds; its data lives inside its own folder; its server
  is not running. Then copy without asking and show a notice listing what was
  copied and from where. In every other case, show one screen with the
  choices preselected.
- **Synced folders are adopted, not copied.** If the older install points at
  an external data folder through its config (Dropbox, Syncthing and so on),
  offer to keep using that same folder. Copying it would split one synced
  campaign into two diverging copies.
- **No duplicates.** Record each copy in a migration ledger in the data
  folder: source path, source world ID, a fingerprint of its `world.json` and
  the new world ID. A world already copied is skipped; one that changed since
  is offered as a separate world, never merged or overwritten.
- **Nothing half-copied.** Stage each world outside `worlds/` and rename it
  in only when complete, as restores do.
- **Skip the untouched sample.** An old sample world identical to the old
  install's own `sample/` folder is not copied.
- **Old version still running:** name it, and ask the tester to quit it
  before copying. From 1.9 onward, the new version can ask an older 1.9+
  instance to quit through its Quit route.
- Library packs (`.library`) are offered with their size, on by default.
- Installed Windows copies and the Mac app already keep data across upgrades.
  This covers portable folders side by side, which is how most testers
  upgrade.

## Share what the players know

| Feature | Change | Acceptance evidence |
| --- | --- | --- |
| Player wiki export | An offline HTML site in a ZIP. It has category indexes, entry pages with visible blocks, facts, portraits and relations, working links and visible backlinks. It also includes the timeline, player map renders with their key, handout pages and search | A canary world's secrets are absent from every file, file name and image in the ZIP, with the text layer checked automatically. The site opens and searches from `file://` with networking disabled |
| Reveal tracking | **Reveal to players** on secret blocks, relations and overlay items, and on GM-only entries. Each reveal is logged on a Session entry and can be undone | Revealed content appears in player preview, the player PDF and the wiki, and undo removes it from all three. The session lists the reveal. The log never reaches player output |
| Safety check | A review before export that finds public text naming hidden entries, labels matching hidden names, reused images of hidden entries and handouts with hidden sources | Each leak class in a fixture world produces a finding with a working link. The sample world produces only expected findings |

Build the player projection first, then the wiki on top of it. Reveal
tracking and the safety check follow, because both are only useful once
there is something to share.

### Player projection contract

- The player wiki, the player PDF and the safety check filter content with the
  same functions: `visibleEntities()`, the block, relation and overlay
  `secret` checks, `projectHandout()` and `mapKey()` numbering. Where pdf.js
  holds private filtering logic, extract it rather than copy it. Two filters
  that disagree would repeat the two-comparator failure described in AGENTS.md.
- Never expose entity IDs, world IDs or asset file names in player output.
  `newEntity()` derives an ID from the name an entry was created with, and
  the ID survives renames. Uploaded images keep their original file names.
  Either can reveal a name the GM has since hidden. Use generated page names
  and content-hashed image names.
- Copy only the images that projected content references. Build the search
  index from projected text only.
- The site must work from `file://` with networking disabled. Browsers block
  `fetch` of local files, so page data and the search index load through
  ordinary `<script src>` files. Nothing comes from the web: no fonts, scripts
  or images.
- Chronology uses the kernel: `isHistoric()`/`isRecurring()` before sorting,
  `histSortKey`/`slotSortKey` with `cmpKey`, and `formatDate`. Age bands come
  from the already-filtered list, so the timeline matches the app and the PDF.
- Links to hidden entries render as plain text, as in the app. The safety
  check reports them before export.
- Ship the player edition only. A GM edition would be a second, easily
  forwarded copy of every secret. The GM already has the app and backups.
  Every page states the edition and export date.

### Reveal model

- A reveal flips one existing flag: a block's `secret`, a relation's `secret`,
  an overlay item's `secret` or an entry's `gmOnly`. It adds no flag and
  copies no content.
- Each reveal appends a record to an optional `entity.reveals` list on a
  Session entry. A record holds a stable reference to what changed, its
  previous value and the time. It holds references only, never text.
- The reveal dialog names the session it will log to: the one last selected
  in the Encounter view, otherwise the most recently updated Session entry.
  The GM can change it.
- Undo restores the previous value only when the flag has not changed since.
  Otherwise it explains why not.
- `reveals` is GM-only and excluded from every player output, like
  `sessionTracker`. Reveal controls never appear in player preview.

### Safety check

- The check runs before every player PDF and player wiki export, and on
  demand from the Export page. Findings never block an export. Each one links
  to the place where it can be fixed.
- It reports:
  - public text (blocks, quick facts, table rows, captions, handout text) that
    contains a GM-only entry's name as a whole phrase, ignoring case;
  - free map labels and overlay labels that equal a hidden entry's name;
  - images of hidden entries that visible content reuses;
  - handouts whose source entry is hidden, with an explanation of what
    `projectHandout()` omits.
- The check only analyzes and never edits content. Findings are recomputed
  each time, and no dismissal state is stored.

## Maps you can run

| Feature | Change | Acceptance evidence |
| --- | --- | --- |
| Map keys | Prep notes attached to dungeon rooms, generated settlements and landmarks, town landmarks and region hexes, with a numbered GM key in PDFs | Keyed notes survive renames and reloads. Repainting a room moves its note to Unplaced notes without loss. Maps without keys render byte-identically |
| Populate a settlement | One-click drafts of people and places for a town's districts. They are previewed before creation, then created GM-only with relations and linked markers | A second run creates no duplicates. Nothing appears in player preview until revealed. Map hashes are unchanged |
| Journey planner | A route between region settlements over roads and ferries, with distance, travel days, an optional clock advance, daily table rolls and a session note | A ferry crossing is routed and labeled. The clock advance crosses month ends and intercalary days correctly. Rolls are never stored |
| Modern towns | A new town era for modern settings: avenues down to cul-de-sacs, downtown, suburbs, industrial and civic districts, parks, parking, a rail line and station, bridges and a waterfront, in a clean modern map style | Legacy and 1.8 town hashes are unchanged. Each modern layout is deterministic, readable at print size, and works with map keys, Populate and journeys |

Start with dungeon rooms, the most requested key and the simplest anchor.
Settlements, town landmarks and hexes follow on the same mechanism. Populate
and journeys depend on it. Modern towns are independent of the other three
and can be built in parallel.

### Map key contract

- Anchors:
  - A dungeon room is anchored to a cell `{x, y, level}` inside it.
    `numberRooms()` recomputes numbers from the grid on every render, so a
    stored number would drift. The number is derived from the anchor cell
    instead.
  - Generated settlements and landmarks keep their existing site keys.
  - Town landmarks receive site keys in the same `kind:index:generated-name`
    form, attached after generation.
  - A hex is anchored by column and row on the region's fixed-size hex
    overlay.
- Store anchors in an optional `map.keys` object. Each maps an anchor to a
  block ID on the same entry, or to an entity ID when a place is promoted to
  its own entry. Notes are ordinary blocks and entries, secret by default, so
  the existing flags govern them.
- Key numbers and notes draw in the overlay pass. No generator stream is read
  and no model is written. Maps without keys render as before.
- An anchor may stop resolving after a repainted room, a hidden or
  regenerated site, or a disabled hex overlay. Its note then appears under
  **Unplaced notes** with **Re-anchor** and **Remove anchor**. Nothing deletes
  a note.
- The GM PDF prints each map's key after the map, per dungeon level and in
  number order. Player output never prints key notes. Room numbers for
  players follow the 1.8.3 export choice.

### Populate contract

- Populate works on 1.8 towns and modern towns, because both carry district
  uses. Each era has its own role tables.
- Suggestions come from original, system-neutral tables and `names.js` on a
  new `':populate'` stream. Populate never reads or advances a generator
  stream and never writes the map model.
- Populate previews before it applies, like regeneration. **Apply** creates
  GM-only entries, each with a relation to the town and a linked marker on a
  building of the matching district. Nothing is written before Apply.
- Running it again offers only roles not yet filled. It never duplicates a
  linked entry.
- Publishing a generated place is an ordinary reveal.

### Journey contract

- Region maps come first. World maps have no road network and are out of
  scope for 1.9.
- The route is a deterministic shortest path over roads and 1.8 ferry routes,
  with ties broken by site key. No RNG is used.
- Distance requires the map's distance scale (`params.distance`). Days come
  from an editable pace table (foot, mounted, cart, ship, and car and train
  for modern settings) with generic defaults, not rules text.
- Applying a journey adds an ordinary Travel route path, undoable through map
  history. It can also advance the campaign clock through `calendar.js`
  arithmetic, declining invalid dates rather than clamping them. It can
  append a secret text block to the chosen Session with the route, distance
  and dates.
- Daily rolls on a linked random-table block stay ephemeral, as in 1.1. They
  are shown in the planner and never stored unless the GM copies them into
  text.

### Modern town contract

- A new town param `era`: absent means the existing historical look, and
  `'modern'` selects the new path. The generator reads `map.params?.era`
  directly, never the defaults-merged params (the atlas-style rule), so no
  existing map can change. New town maps choose their era when created.
- Modern generation draws only from its own streams under a `':modern'`
  prefix. It never reads or advances legacy or 1.8 streams. It reuses the 1.8
  street, block and parcel machinery in `townplan.js` where that fits, with
  its own parameters.
- The model has street classes (arterial, collector, local, cul-de-sac),
  blocks and lots with setbacks, building footprints by district, parking
  lots, parks, a rail line and station, bridges and a waterfront.
- Districts: downtown and commercial, residential (dense and suburban),
  industrial, civic, parkland and waterfront. Modern landmarks (police
  station, hospital, school, city hall, diner, gas station, motel, library,
  church, train station, marina, warehouse) serve labels, map keys and
  Populate.
- Rendering uses a clean modern style: flat fills, road casings by street
  class and sans-serif labels. A night palette is a render-level theme, which
  suits Vampire chronicles. Themes never touch the model, like town themes.
- Street and business names come from original tables and stay editable, like
  ward names.
- The era param leaves room for another era later, such as 1920s towns for
  Call of Cthulhu, without new machinery. World and region maps have no era
  in 1.9; a drilled town takes the era chosen when it is created.

## Character sheets players recognize

| Feature | Change | Acceptance evidence |
| --- | --- | --- |
| Familiar sheet layouts | A new screen and print layout for each system that follows the standard sheet's structure: the same sections, in the same order and positions, with the same field names and visual conventions (dot tracks, damage boxes, skill lists grouped the same way). The current original layout and Compact text stay available | Testers who play each system find every value without being told. Secret banners, continuation pages and player redaction behave exactly as in the existing layouts |

### Layout contract

- Each system gets one section map (field to page region), documented in the
  design notes and derived from the publisher's current free sheet. Values
  come from the existing sheet data; the data model does not change.
- The in-app sheet and the PDF follow the same section map, so screen and
  print agree, as handout preview and export do.
- All dynamic text still goes through the `safe` option (`pdfSafe`), and every
  continuation page repeats the GM or secret banner.
- A4 and US Letter both print without clipping.
- The familiar layout becomes the default only after tester review.

### Licensing contract

This is load-bearing, like the 0.12 licensing line. "Practically
indistinguishable" is limited by what the project may reproduce:

- Game terms, field names, section order and the arrangement of fields are
  followed closely.
- Publisher logos, trademarks, artwork, decorative borders, backgrounds and
  fonts are not copied. Every ornament is drawn for the project, and fonts
  are bundled or system fonts.
- The UI never calls the layout "official" and never implies endorsement.
- Before release, record for each system which terms apply and what they
  allow: SRD 5.2.1 (CC-BY-4.0) for D&D rules text, which does not cover the
  sheet's design; Chaosium's fan-use terms for Call of Cthulhu; the Dark Pack
  agreement for V5, which the project already uses for its logo
  (`public/vendor/dark-pack.webp`). Where terms allow more, use exactly what
  they allow and credit it in Settings → About.
- An exact official look is possible without redistributing anything: the GM
  downloads the publisher's own fillable PDF and MundusMaker fills its form
  fields locally. See Decisions to confirm.

## Quality and performance gates

Legacy and 1.8 map hashes must pass unchanged whenever a feature is unused.
Add hash fixtures for a keyed dungeon, a map with a journey route and each
modern town layout once their drawing settles.

A `node:test` canary suite covers the wiki's text layer: page text, search
index, file names and relation labels. It follows the handout projection
tests. Map images are inspected visually, as in 1.8.

Upgrade tests are hermetic, like `tests/installed-config.test.js`: fake older
installs in temporary folders, covering the v1 layout, an external configured
data folder, the untouched-sample rule, the ledger and an interrupted copy.
They never touch `data/`.

Launchers are checked on Windows at every release. Mac and Linux behavior
needs native machines; the release notes say which platforms were verified
natively, as the 1.8.1 notes do.

Character sheets are reviewed side by side with each publisher's current free
sheet by testers who play that system, on screen and on paper.

A generated 2,000-entry world tests scale in scratch data, never `data/`. It
covers the safety check, unlinked mentions, search index size and export
time. Initial targets on the documented laptop: the safety check and unlinked
mentions under two seconds; the player wiki without map images under 30
seconds. Revise the targets after the first measurement.

Test the wiki from `file://` with networking disabled in Edge or Chrome and in
Firefox. Test Safari only if a Mac is available.

## Required regression scenarios

- Open legacy and 1.8 maps that have no keys or journeys. They must hash
  identically before and after 1.9.
- Launch on Windows from the Start-menu shortcut and from the portable folder.
  Confirm no console stays open. Close the browser, reopen from the tray, then
  Quit with an unsaved edit pending and confirm it was saved. Launch twice.
  Launch while an older version holds the port.
- Extract 1.9 beside a copy of a 1.8.2 install holding test worlds, never real
  data. Confirm:
  - the worlds are copied automatically;
  - the old folder is byte-identical before and after;
  - a second start copies nothing;
  - a world changed in the old install is offered as a separate world;
  - an external synced folder is offered for adoption, not copied;
  - an interrupted copy leaves nothing half-visible.
- Rename an entry whose ID embeds an earlier name, and upload an image whose
  file name names a secret. Export the player wiki. Neither name may appear in
  any file or file name.
- Reveal a secret block, a secret relation, a secret marker and a GM-only
  entry. Export the PDF and the wiki. Undo each reveal and export again.
- Add a secret block that mentions a GM-only NPC to a public handout, then link
  the handout to a hidden source. Confirm the safety check reports both, and
  that player preview, PDF and wiki omit the protected content.
- Key a crypt room and repaint it away. Confirm the note is unplaced, not lost.
  Regenerate with **Keep current map** and confirm nothing changes.
- Populate a fantasy and a modern town twice each. Confirm there are no
  duplicates, and that nothing appears to players until revealed.
- Plan a journey that crosses a ferry. Advance the clock across a month end
  and an intercalary day. Confirm invalid dates are declined, not clamped.
- Print all three systems in the familiar layout, player and GM editions, on
  A4 and Letter. Grep the player PDFs for secret canaries and confirm every
  continuation page repeats its banner.
- Back up and restore a world with keys, reveals, journeys, packets and
  images into a separate world. Check anchors, links, asset rebasing and the
  reveal log.
- Test with networking disabled. Inspect tester archives for accidental data,
  development files, and any `AGENTS.md` or `CLAUDE.md` at any depth or casing.

## Decisions to confirm

- **Windows launch mechanism.** Recommended: a hidden PowerShell tray host,
  which may flash briefly at start. The alternative, patching a copy of the
  runtime into a windowless executable, avoids the flash but breaks the
  runtime's signature and may alarm antivirus software.
- **Upgrade copying.** Recommended: copy automatically only in the unambiguous
  case and ask otherwise. The alternatives are always asking or always
  copying.
- **Library packs** are copied by default during an upgrade.
- **Character sheet approach.** Recommended: familiar layouts drawn for the
  project. The addition or alternative is filling the GM's own copy of each
  publisher's fillable PDF. That gives the exact official look with nothing
  redistributed, but needs a small PDF form filler and field maps per sheet
  version, which break whenever a publisher updates its PDF.
- **The layout's name in the UI.** It cannot be "official".
- **A world-level default era** for new town maps, or a choice per map only.
- Map key notes default to blocks on the map's own entry, with **Promote to
  entry** for places that deserve one. The alternative, always creating
  separate entries, would clutter the sidebar: a 40-room dungeon means 40
  entries.
- The reveal log's session is the one last selected in the Encounter view,
  otherwise the most recently updated Session.
- The player wiki is player-edition only.
- Populate tables are system-neutral in 1.9.
- Journeys work on region maps only.

## Scope boundaries

MundusMaker remains a local preparation tool. The player wiki is a static file
the GM chooses to share, not a hosted service. There are no player logins,
live updates, shared cursors or fog-of-war. No AI generation, cloud storage
or accounts.

Upgrading stays "extract the new version beside the old one": nothing checks
for or downloads new versions, and old installs are never modified or
deleted. The tester removes the old folder when ready. MundusMaker installs
no operating-system service and does not start at login.

Publisher logos, artwork and trade dress are not reproduced without
permission. Modern styles for world, region, interior and dungeon maps, a
1920s era, multiclassing, moons and weather, journeys on world maps, and
sharing custom handout templates are deferred to later releases.
